# P0.3R Hikvision and CP Plus Device Acceptance Pack

Status: executable acceptance specification. Physical-device observations start as **NOT RUN**. Rows that current code review proves cannot pass are pre-marked **BLOCKED**. Populate only from an authorized run and attach sanitized evidence.

This document validates the Drishti AI standards path against two exact devices. It does not certify an entire vendor family, replace a vendor compatibility programme, establish Milestone device-pack equivalence or prove zero failure.

## 1. Result vocabulary

Use only:

| Result | Meaning |
|---|---|
| `NOT RUN` | no authorized execution/evidence yet |
| `PASS` | observed result met the stated criterion; evidence reference exists |
| `FAIL` | executed and criterion not met |
| `BLOCKED` | could not execute because a prerequisite/permission/implementation was absent |
| `NOT SUPPORTED` | exact device/firmware does not expose the capability; fallback/impact is recorded |
| `NOT APPLICABLE` | test cannot apply to the declared device/configuration, with approved rationale |

`BLOCKED` and `NOT SUPPORTED` are not passes. Do not use “working,” “compatible” or “supported” without the model, firmware, stream role, codec, network conditions, run ID and evidence.

## 2. Required approvals and safety

Before testing:

- identify a lab-owned device or obtain written owner approval and maintenance window;
- use an isolated CCTV VLAN/test switch with documented egress, not an unrestricted government production network;
- obtain permission separately for reboot, service enablement, password rotation, NTP/clock change, firmware change and load/concurrency tests;
- save/approve device configuration recovery without exporting credentials into the repository;
- create a unique credential in an approved secret manager; never paste it into this document, terminal history, URL, screenshot or video;
- synchronize the test host and preserve its time source/offset evidence;
- record switch/NIC/GPU/CPU/software versions;
- stop if testing causes device instability, lockout, production traffic impact or unexpected network discovery.

Never factory-reset, upgrade firmware, change a government-device password/clock, or reboot without explicit authorization.

## 4. Implementation boundary that affects testing

The frozen P0.3R runtime API is:

- `GET /api/v1/federation/runtime/capabilities`;
- `GET /api/v1/federation/runtime/sessions`;
- `POST /api/v1/federation/connections/{connection_id}/runtime/start` (`202`);
- `GET /api/v1/federation/runtime/sessions/{session_id}`;
- `POST /api/v1/federation/runtime/sessions/{session_id}/stop`;
- `POST /api/v1/federation/runtime/sessions/{session_id}/restart`;
- `GET /api/v1/federation/runtime/sessions/{session_id}/playlist.m3u8`;
- `GET /api/v1/federation/runtime/sessions/{session_id}/segments/{asset_name}`.

Public states are `starting`, `live`, `degraded`, `backoff`, `stopped`, `failed`, and `unavailable`.

Important baseline limitations:

1. `onvif` profiles now perform authenticated Media1 `GetCapabilities`, `GetProfiles`, and `GetStreamUri`; `vms_http` remains `unavailable` until a vendor driver resolves an authorized media URI. WS-Discovery is not implemented.
2. Local `credential-profile:<uuid>` identities are encrypted, write-only, enabled-state checked and department-scoped. External Vault/KMS references remain fail-closed until an approved workload-identity resolver exists.
3. ONVIF and credentialed direct RTSP are code-complete baselines but remain `NOT RUN` for both vendors until the physical rows below produce evidence.
4. A P0.3 lightweight `reachable` probe is not runtime, codec, playback or credential success.
5. HLS asset routes require authentication/resource authorization in production. If the current build only has the prototype actor header, mark shared-network authorization tests `BLOCKED` and keep the demo on isolated loopback.
6. Direct RTSP handoff is rewritten to a policy-approved IP and FFmpeg protocols are adapter-limited. HLS/MJPEG host resolution and HLS child/key/map destinations are not pinned; treat HTTP-family runtime egress as `BLOCKED` outside an isolated test network.

These limitations are expected security outcomes, not reasons to fabricate a pass.

## 7. Execution sequence

### Phase A: inventory and safe preflight

1. Complete device/environment identity and approvals.
2. Confirm test-host NTP, build hash, FFmpeg version and runtime capabilities.
3. Confirm runtime root is private, bounded and outside any public static root.
4. Confirm no endpoint/credential appears in command history, environment capture or screen recording.
5. Record current device service/profile settings without changing them.

### Phase B: ONVIF and RTSP protocol qualification

Use an approved secret-safe ONVIF/RTSP harness whose invocation does not expose credentials. Capture sanitized structured results, not raw URIs/headers. Correlate ONVIF profile token to the primary/substream observed properties.

If ONVIF is disabled/unsupported, record `NOT SUPPORTED` and the operational impact. Manual direct RTSP may continue as a limited standards path, but it does not earn ONVIF discovery/profile acceptance.

### Phase C: Drishti runtime and HLS

1. Create one department-scoped managed credential through the write-only portal and safe P0.3 profiles for direct RTSP and ONVIF device service.
2. Verify cross-department, disabled-profile and unconfigured external-resolver references fail before spawn.
3. For authorized direct or ONVIF-resolved sources, call asynchronous start and poll safe status.
4. Assert `live` only after output freshness evidence.
5. Fetch playlist/segments through the protected API and execute negative authorization/traversal/cache checks.
6. Exercise an isolated DNS-rebinding/redirect/HLS-child-URI fixture and prove the media worker cannot reach the disallowed destination; a lightweight-probe-only result does not pass.
7. Stop and verify process/assets/generation cleanup.

Do not work around resolver policy by embedding userinfo, using a shared/default password, or disabling redaction.

### Phase D: resilience

Run one fault at a time with synchronized observation:

- planned reboot;
- 60-second network isolation;
- extended isolation through circuit threshold;
- password rotation after resolver integration;
- supervisor restart;
- media stall/no-output condition;
- disk/capacity denial in an isolated worker.

Record fault time, detection time, state transitions, retries/delays, restore time, `live` recovery time and any orphan/duplicate process.

### Phase E: codec and resource

Test H.264 primary/substream copy, then approved H.265. Do not assume browser HEVC. Record whether the runtime chose H.264 substream, hardware/software transcode or honest unavailable. Capture exact GPU/CPU path and output properties.

## 8. Timing and resilience criteria

Configuration-relative pass criteria avoid inventing a universal camera RTO:

- startup: `live` only after a fresh complete manifest/segment within configured startup deadline;
- stale detection: no later than watchdog interval + freshness threshold + configured grace, all recorded;
- retry: actual delay within configured full-jitter cap and no site/host budget breach;
- recovery: after source becomes reachable, within current backoff remainder + startup deadline, unless circuit requires authorized half-open;
- stop: no owned process after terminate grace + force-kill/reap bound;
- circuit: no automatic spawn while open; only one half-open generation;
- clock: route/time-critical target <=2 seconds absolute offset and <=1 second/hour observed drift, or mark time quality degraded.

For the hackathon preview, declare a latency target before execution. A reasonable LAN H.264-remux target can be measured against <=6 seconds p95 with a compatible GOP/segment configuration, but it is not a product guarantee and must be reported as failed if not met.

## 12. Claim language after testing

Allowed form:

> The standards-based P0.3R runtime was tested against the listed Hikvision and CP Plus models/firmware under the recorded conditions. The report states passed, failed, unsupported and blocked cases plus measured recovery/resource results.

Not allowed:

- “supports all Hikvision and CP Plus cameras”;
- “equivalent to Milestone Device Pack”;
- “zero failure” or “100% uptime” from a finite soak;
- “80,000 streams supported” from registry cardinality or a 50-feed PoC;
- “secure live view” while identity/authorization, physical credential tests, or critical process isolation remain blocked.
