# P0.3 Stream Federation Threat Model

Status: current P0.3 security-review baseline. It is not an authorization to connect production feeds.

## 1. Scope

This threat model covers P0.3 connection-profile onboarding, encryption at rest, adapter selection, lightweight protocol probes, normalized probe metadata, audit, and the operator-facing federation UI.

It excludes sustained decoding, browser live view, recording, analytics, detections, watchlists, alerts, and evidence handling. Those data-plane functions require their own P0.4 threat model and must not inherit a production approval from this document.

## 2. Security objectives

1. A browser or ordinary read caller cannot recover a raw endpoint or credential reference.
2. Database theft alone does not reveal protected connection material.
3. A submitted endpoint cannot turn the service into a general-purpose network scanner or proxy.
4. DNS, redirects, proxy behavior, alternate IP representations, and protocol parsing cannot bypass egress policy.
5. A defective or compromised adapter is contained and cannot destabilize the control plane.
6. Probe results, errors, metrics, logs, traces, and audit expose only normalized, non-secret metadata.
7. Every material profile and probe action is attributable and reviewable.
8. Availability controls prevent a feed, operator, or department from exhausting shared worker capacity.
9. Cryptographic key rotation and recovery do not require plaintext export or silent data loss.

## 3. Assets and classification

| Asset | Classification | Principal risk | Required handling |
|---|---|---|---|
| Raw camera/VMS endpoint | restricted operational topology | disclosure enables targeting and lateral movement | encrypted at application layer; write-only API field; never logged or returned |
| Credential reference | restricted secret metadata | reveals vault path/identity and can aid privilege escalation | protected with the endpoint; resolve server-side only |
| Credential value | secret | direct unauthorized camera/VMS access | never stored by P0.3; resolve just in time from a managed secret store |
| Encryption keys | critical secret | bulk profile compromise or irrecoverable data | never in database/source control; managed key custody, rotation, backup, access audit |
| Camera/profile UUIDs | sensitive internal metadata | enumeration and cross-department inference | resource-scoped authorization; avoid public indexing |
| Department/location metadata | sensitive operational metadata | surveillance coverage disclosure | role/department/district access policy and audit |
| Normalized probe result | sensitive operational telemetry | reveals outages and capability posture | safe fields only; access control and retention policy |
| Audit history | integrity-critical record | repudiation or cover-up | append-oriented storage, trusted identity, protected export/retention |
| Adapter package/image | privileged executable | supply-chain compromise and worker escape | pinned/signed artifacts, scanning, SBOM, isolated execution |

## 4. Trust boundaries

```text
[Operator browser]
      |
      | Boundary A: untrusted client -> API
      | (authentication is a production gate)
      v
[API / authorization / validation]
      |
      +---- Boundary B: application -> encrypted database
      |
      +---- Boundary C: orchestrator -> adapter worker
      |                         |
      |                         +-- Boundary D: worker -> DNS/network target
      |
      +---- Boundary E: worker -> secret manager/KMS
      |
      +---- Boundary F: application -> audit/log/metrics systems
```

Boundary A treats all browser input as untrusted. Boundary C treats adapter output and third-party library errors as untrusted. Boundary D is the highest-risk transition because it reaches camera/VMS networks. Boundary E is permitted only through workload identity and least privilege.

The **Baseline** column is the P0.3 implementation target that must be evidenced by tests. The **Production** column is mandatory before real government feeds, even when not implemented in the local proof of concept.

## 6. Endpoint-policy algorithm

Every network adapter follows this fail-closed sequence:

1. Parse using a standards-aware URI parser; reject control characters, ambiguous encodings, fragments where unsupported, and embedded user information.
2. Require a scheme declared by the selected adapter manifest and a permitted port policy.
3. Canonicalize the hostname/address without resolving path content into logs.
4. Resolve all A and AAAA results with a trusted resolver.
5. Normalize addresses, including IPv4-mapped IPv6, then reject special/reserved classes.
6. Require every private or loopback resolved address to be contained by an explicitly configured CIDR. The evaluation baseline permits public unicast after the preceding checks.
7. Connect directly to one of the approved resolved IPs while preserving the hostname only where protocol semantics require it; do not hand the hostname back to a client that re-resolves independently.
8. Disable redirects, as the current HTTP-family probes do, or repeat the complete validation for every redirect target in a future client.
9. Disable ambient proxy inheritance.
10. Enforce the approved production destination policy through operating-system/container egress rules or a controlled egress proxy.

An endpoint fingerprint may be calculated from a keyed digest of a canonical endpoint for correlation without disclosure. A plain unsalted hash of a small, guessable endpoint space is not sufficient protection.

## 7. Cryptographic design and operations

### Implementation baseline

- use an authenticated-encryption construction supplied by a maintained cryptographic library;
- authenticate ciphertext before returning plaintext;
- associate each record with a non-secret key identifier/version;
- never invent a custom cipher or store the active key in the same database;
- fail protected operations closed when key configuration is missing or malformed; production readiness must fail before traffic is accepted;
- never fall back to plaintext or a hard-coded development key;
- prevent encryption/decryption errors from echoing data;
- include wrong-key, corrupted-ciphertext, and absent-key tests.

The implementation-specific environment name, key format, and key-generation command are frozen in the local runbook only after the backend contract is confirmed. No sample in this repository may be a deployable shared key.

### Rotation procedure

1. Inventory ciphertext counts by non-secret key ID; do not export protected values.
2. Generate the new key in the target secret manager/KMS under dual control.
3. Grant the application a temporary decrypt-old/encrypt-new permission set.
4. Enable a bounded dual-key read window and make all new writes use the new key.
5. Re-encrypt records in small idempotent batches with row/version locking; because the endpoint fingerprint key is derived from the encryption key, recompute the keyed fingerprint atomically for each migrated endpoint.
6. Read back and authenticate each migrated record before committing the new ciphertext.
7. Compare total/success/failure counts and investigate every failure.
8. Keep the old key disabled from new writes but recoverable through the rollback window.
9. Take and test an encrypted backup plus independent key escrow/recovery evidence.
10. Revoke ordinary access to the old key; destroy it only after retention and recovery approval.

### Backup/recovery rules

- Database backup and key backup have independent access paths and custodians.
- A backup is incomplete until a restore can decrypt an authorized sample and audit that access.
- Losing every copy of a retired key makes its ciphertext irrecoverable; key-retention follows backup retention.
- Exposing the database and its matching key defeats application-layer encryption; incident response treats that combination as a critical breach.
- Recovery drills record RPO/RTO observations rather than untested promises.

## 8. Abuse cases to automate

At minimum, security tests should cover:

- endpoint with clear-text or percent-encoded user information;
- decimal/hex/octal IPv4 variants and IPv4-mapped IPv6;
- loopback/private targets outside the explicit CIDR plus link-local, multicast, unspecified, reserved/documentation, and cloud-metadata ranges;
- public-unicast acceptance under the evaluation policy and rejection under the stricter production egress profile;
- a private address outside the configured allowlist;
- hostname resolving to mixed allowed and denied addresses;
- DNS answer changing between validation and connect;
- redirect from allowed target to denied target;
- proxy environment variable present;
- HLS child/key URI pointing to a denied host;
- oversized/stalled/malformed RTSP, HTTP, XML, playlist, and multipart responses;
- ONVIF external-entity and expansion payloads;
- recorded-file traversal, absolute path, symlink, and URI input;
- corrupted ciphertext, wrong key, missing key, and unknown key ID;
- endpoint/credential canary absent from JSON, errors, logs, audit, metrics, and frontend bundle/state;
- unauthorized cross-department list/read/update/probe/disable attempts once identity exists;
- high-rate probes and one deliberately slow target to validate bulkheads and deadlines.

## 9. Residual risks and acceptance authority

The local P0.3 baseline may still execute adapters in the API process, use a process-supplied encryption key, use unverified actor headers, and lack production identity/network enforcement. Those limitations are acceptable only for sanitized, isolated local demonstration inputs.

No real government feed, private topology, or credential reference should be introduced until the production controls relevant to its environment have named owners, test evidence, and formal approval. Product functionality, a successful demo probe, and this threat model do not replace that authorization.
