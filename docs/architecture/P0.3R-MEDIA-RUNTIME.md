# P0.3R Supervised Media Runtime

Status: reliability architecture and implementation-review contract for the P0.3R increment. The running OpenAPI document, automated tests, and measured device-acceptance evidence remain authoritative.

This document uses three labels:

- **P0.3R baseline** means behavior that must be visible in repository code and tests before it is demonstrated as implemented.
- **Production gate** means mandatory hardening before a real government feed, credential, or operational network is connected.
- **Scale target** means the intended statewide design, not a measured capacity result.

## 1. Purpose and boundary

P0.3 proved that heterogeneous source endpoints can be represented as encrypted, vendor-neutral connection profiles and checked with bounded protocol probes. P0.3R adds a supervised media-runtime path: start an authorized profile, keep a standards-based media worker healthy, produce a short-lived browser-safe HLS window, and stop/clean it deterministically.

P0.3R is the reliability bridge between connection onboarding and P0.4 analytics. It should answer:

- Is a sustained media process alive and producing fresh output?
- If it fails, which deterministic state and safe reason describe the failure?
- Will reconnect/backoff behavior protect the source and platform from a retry storm?
- Can an authorized operator retrieve only the runtime's bounded HLS assets?
- Is the source being remuxed or transcoded, and what resources does that consume?
- Can the session be stopped without leaving a child process, secret-bearing file, or stale asset behind?

P0.3R does **not** claim recording/evidence retention, ANPR, face recognition, watchlist matching, alerting, vehicle routes, forensic export, PTZ control, or statewide performance. Browser playback is a supervised preview path, not an evidence chain.

## 2. Standards path versus a Milestone device pack

Drishti AI follows an **Agent-DVR-style standards path** as an architectural pattern: ONVIF for standards-based discovery/profile metadata where supported, RTSP/HLS/MJPEG inputs, and FFmpeg-compatible media processing. This phrase describes an approach; it does not assert that Agent DVR code, certification, or compatibility data is part of this repository.

Milestone XProtect Device Pack and comparable commercial VMS products use curated, versioned native drivers and extensive vendor/model/firmware validation. A native driver may expose proprietary events, edge storage, audio, I/O, PTZ, analytics metadata, or firmware-specific workarounds that a generic ONVIF/RTSP path does not.

| Dimension | P0.3R standards runtime | Commercial native device-pack model |
|---|---|---|
| Integration unit | protocol adapter + generic media worker | vendor/model/firmware-specific driver |
| Discovery | configured ONVIF/standards flow where implemented | curated driver/device discovery behavior |
| Media | RTSP/HLS/MJPEG or controlled file through FFmpeg-compatible tooling | vendor-qualified streams through native/standards drivers |
| Device features | only explicitly implemented standard functions | potentially proprietary events, PTZ, I/O, edge storage and audio |
| Compatibility evidence | exact tested device, firmware, codec, profile and network conditions | vendor/product compatibility program and published support matrix |
| Upgrade response | regression-test affected adapters/devices | device-pack lifecycle supplied by the VMS vendor |
| Claim boundary | interoperability prototype and measurable standards path | mature commercial VMS capability, subject to vendor terms |

Passing the Hikvision and CP Plus acceptance matrix in this repository proves only the tested models, firmware, profiles, codecs, credentials and network conditions. It does not prove all models from either vendor and is not Milestone equivalence.

## 3. Logical architecture

```text
                             CONTROL PLANE

  Operator / internal caller
             |
             v
  Runtime API + authorization gate
             |
      connection UUID only
             v
  P0.3 profile service -------------------> audit + safe runtime status
     | decrypt endpoint just in time
     | department-scoped credential resolver
     | ONVIF Media1 negotiation when selected
     v
  Session supervisor / state machine
     | lease + generation + monotonic deadlines
     | spawn / observe / stop / reap
     v
  Isolated FFmpeg standards worker
     | RTSP/HLS/MJPEG/ONVIF-resolved RTSP/file input
     | remux H.264 or transcode under policy
     v
  Per-session private media directory
     | bounded HLS playlist + segments
     v
  Authorized HLS asset gateway ----------> browser preview

                     EDGE / STATEWIDE TARGET

  Central scheduler -> regional queue -> site/edge supervisors
                                      -> normalized status/events centrally
```

The central API owns intent and safe status. The media worker owns protocol parsing and codec execution. The asset gateway owns authorization and file delivery. None of these responsibilities should silently collapse into a public static-file directory.

## 4. Runtime resource model

A runtime session is subordinate to one P0.3 connection profile and therefore one P0.1 camera. The frozen P0.3R API uses:

- `GET /api/v1/federation/runtime/capabilities`;
- `GET /api/v1/federation/runtime/sessions`;
- `POST /api/v1/federation/connections/{connection_id}/runtime/start` returning `202`;
- `GET /api/v1/federation/runtime/sessions/{session_id}`;
- `POST /api/v1/federation/runtime/sessions/{session_id}/stop`;
- `POST /api/v1/federation/runtime/sessions/{session_id}/restart`;
- `GET /api/v1/federation/runtime/sessions/{session_id}/playlist.m3u8`;
- `GET /api/v1/federation/runtime/sessions/{session_id}/segments/{asset_name}`.

Start/stop/restart are intent operations; asynchronous acceptance is not proof that FFmpeg reached `live`. Callers inspect the safe session resource.

The frozen safe session representation contains exactly:

- `id`, `connection_id`, and supervisor `state` (`starting`, `live`, `degraded`, `backoff`, `stopped`, `failed`, or `unavailable`);
- safe `camera` identity (`id`, code, name, department name, district and city) and safe `profile` identity (`id`, name, adapter kind, stream role and masked `endpoint_display`);
- `playlist_url`, or `null` when the session is not active;
- bounded `metrics` (`frame`, `fps`, `out_time_ms`, `progress_at`);
- `restart_count`, `started_at`, `state_changed_at`, `last_progress_at`, `last_playlist_at`, and `stopped_at`;
- safe `last_error_code` and `last_error_message`.

It must not return the decrypted input endpoint, credential reference/value, FFmpeg command line, environment, process working path, playlist filesystem path, resolved private IP, raw stderr, or secret-bearing vendor output.

The current manager permits one active session per connection. A duplicate start returns `409 RUNTIME_SESSION_ACTIVE`; it does not spawn a second worker. Stop is effectively idempotent for a known session. Production reliability should add durable generation/fencing identity and optimistic lease checks so an old watchdog cannot terminate or overwrite a newly started process.

The current safe session schema does not publish requested/effective codec mode, bitrate, resolution, hardware acceleration, generation, next-retry time or circuit state. Those fields are required before operators can distinguish remux from transcode or make capacity/circuit claims. The capabilities response does declare `video_processing_mode=software_h264_transcode`, a configured `max_active_sessions`, safe network-handoff labels, the credential-resolver mode and `boundary=process_local_poc`; those capability labels describe policy/limitations, not measured throughput.

### 4.1 Observed proof-of-concept implementation and mismatches

As of this P0.3R review, the repository implements a `process_local_poc` manager with in-memory sessions and these boundaries:

- eligible adapters are `rtsp`, `hls`, `mjpeg`, ONVIF Media1 and `recorded_file`; `vms_http` creates a safe `unavailable` session;
- the encrypted database resolver accepts only enabled `credential-profile:<uuid>` identities owned by the camera's department. External Vault/KMS references remain fail-closed;
- ONVIF performs bounded WS-Security UsernameToken authentication with HTTP Digest fallback, resolves Media1 capabilities/profiles/stream URI, chooses the lowest profile for `substream` and highest observed profile otherwise, and independently revalidates every derived endpoint. WS-Discovery, Media2, PTZ and vendor extensions are not implemented;
- FFmpeg is resolved from configured path, system path or packaged fallback and runs as a child process with `shell=false`, a scrubbed environment and a new process group;
- FFmpeg receives a fixed adapter-specific protocol whitelist, recorded files are revalidated beneath the media root, and direct RTSP is rewritten to the P0.3 policy-resolved IP; the capabilities response exposes these handoff limits without disclosing the address;
- the safe response omits raw endpoint, ciphertext, credential reference, argv, PID, worker directory and stderr;
- runtime state is lost on API process restart; no durable lease/fencing/reconciliation store exists;
- every source is currently software-transcoded with `libx264`; H.264 stream copy, explicit H.265 policy, hardware acceleration and admission control are not implemented;
- the source endpoint—including a managed authenticated URI—is omitted from process arguments and supplied through a one-entry FFconcat manifest on protected stdin (`pipe:0`); manifest-breaking input is rejected and sanitized stderr lines redact both raw and normalized endpoint forms;
- watchdog health observes process status, FFmpeg progress and playlist media-sequence/last-segment signature advancement, but it does not open and verify a complete non-zero segment before declaring freshness;
- retry uses capped exponential full jitter with a minimum delay and maximum restart count. Per-device/site budgets, a rolling failure-rate circuit, cooldown and automatic half-open are not implemented;
- each retry increments an internal generation and uses generation-qualified segment names; stop removes generated assets and non-active sessions cannot fetch them. Restart still reuses the same session UUID/directory, generation is not part of the public/lease contract, and durable fencing/reconciliation is absent;
- playlist directives are allowlisted, segment names are regex/containment checked, and segments are opened by descriptor with no-follow where the OS supports it. Current routes still have no real authentication/ABAC, and platform-specific hardlink/reparse and cleanup races require qualification;
- P0.3's lightweight probe and the runtime pin direct RTSP to a policy-approved resolved IP. HLS and MJPEG handoff still passes the hostname for FFmpeg resolution, and an HLS manifest can introduce child/key/map requests that did not pass host policy. The FFmpeg protocol whitelist reduces scheme exposure but does not enforce destination, so DNS rebinding and second-order SSRF remain production blockers for HTTP-family inputs.

These are explicit gaps, not hidden implementation details. The remaining sections define the reliability/security target and the evidence required to close them.

## 5. Supervisor state machine

The public serialized states are frozen as `starting`, `live`, `degraded`, `backoff`, `stopped`, `failed`, and `unavailable`. This is the target transition model; the current process-local manager implements the states but not durable generations, full circuit policy or reconciliation:

```text
                                  recovery
                 +----------------------------------------+
                 |                                        |
STOPPED -> STARTING -> LIVE -> DEGRADED -> BACKOFF -> STARTING
   ^          |        |         |            |
   |          |        |         |            `-- retry due
   |          |        |         |
   |          +--------+---------+-- terminal/circuit --> FAILED
   |                                                       |
   +---------------- stop/restart reconciliation ----------+

capability/driver absent --------------------------------> UNAVAILABLE
```

`stopping`, `reconnecting`, `half_open` and `circuit_open` may exist as internal supervisor phases but are not public API states. While an automatic retry is scheduled the API reports `backoff`. When the circuit suppresses retries or manual intervention is required, it reports `failed` with a stable circuit-open-style error code and safe next-action/timing metadata. A one-shot half-open attempt reports `starting` under a new generation.

Required transition rules:

| From | Event | To | Required action |
|---|---|---|---|
| `stopped` | authorized start | `starting` | allocate generation and private directory; resolve protected material |
| `starting` | verified fresh manifest/segment | `live` | persist ready time and output metadata |
| `starting` | spawn/codec/auth/network failure | `backoff` or `failed` | reap process, classify safe error, increment consecutive failure count |
| `live` | process alive but output exceeds freshness threshold | `degraded` | record watchdog reason; do not call stale output healthy |
| `degraded` | progress resumes within grace | `live` | clear transient error without resetting all history |
| `degraded` | grace expires/process exits | `backoff` | internally reconnect/reap generation, remove incomplete assets, schedule retry |
| `backoff` | due time and budget available | `starting` | create a new generation; never reuse stale PID/assets |
| any active state | authorized stop | `stopped` after internal stop phase | cancel retry/watchdog, terminate process group, wait, then force-kill within bound |
| `backoff` | consecutive threshold/window exceeded | `failed` | open internal circuit, suppress automatic starts and expose safe reset/cooldown requirement |
| `failed` | cooldown + authorized restart | `starting` | allow one half-open generation, not a herd |
| any | runtime executable/driver capability absent | `unavailable` | fail closed without spawning |

**Production gate:** unexpected process exit, supervisor restart, or host reboot reconciles persisted intent with observed processes/directories. Unknown PIDs are never trusted only because a numeric PID matches; use generation identity and process ownership. Orphaned workers are terminated before a new generation starts. The current in-memory manager stops children during an orderly application shutdown but cannot claim crash/host-reboot reconciliation.

## 6. Watchdog, reconnect and circuit breaker

### Watchdog inputs

The production watchdog combines signals rather than treating process existence as health:

- child process exit status;
- monotonic time since last FFmpeg progress signal;
- HLS manifest modification time;
- newest complete segment modification time and non-zero size;
- playlist sequence advancement;
- optional safe frame/packet counters;
- disk-space and worker resource pressure;
- connection/profile enablement and camera retirement state.

Wall-clock timestamps are for audit/display. Deadlines, freshness and backoff use a monotonic clock so NTP/device clock changes cannot shorten or extend safety windows.

The current PoC already combines process state, FFmpeg progress and a changing playlist signature derived from media sequence plus last segment. It does not yet open that segment to prove regular-file type, non-zero size and completion before `live`; the acceptance pack keeps this as a blocked production criterion.

### Backoff policy

The reliability target uses capped exponential backoff with full jitter, for example a policy-defined base and cap:

```text
maximum_delay = min(cap, base * 2^consecutive_failures)
actual_delay  = random(0, maximum_delay)
```

Exact base, cap, freshness threshold, startup deadline, threshold count and rolling window must be configuration with validated bounds and observable effective values. Retry counters reset only after a defined stable-running interval, not immediately after one segment. The current PoC now draws retry delay across the capped interval (with a 250 ms floor), which qualifies as bounded full jitter; it still lacks a stable-running reset policy and device/site budgets.

Apply bulkheads and budgets at four levels: connection, device host, site/department and worker node. A 50-camera network outage must not cause 50 synchronized reconnect loops. Manual starts do not bypass circuit/rate policy without a privileged, audited override.

### Circuit breaker

The production circuit opens after the configured consecutive failures or failure rate within a rolling window. The public session is `failed` with a safe circuit error while open. The current PoC implements only a maximum-restart terminal `failed` state and manual restart, not cooldown/half-open behavior:

- no automatic FFmpeg process is spawned;
- HLS assets are revoked/expired;
- the API returns `failed`, a safe failure reason, next eligible time and manual-reset policy;
- one half-open attempt is permitted after cooldown;
- successful recovery requires the stable-running interval.

There is no valid claim of “zero failure.” Reliability is demonstrated by bounded detection, deterministic recovery, failure isolation and measured recovery time.

## 7. Process and secret isolation

### Process boundary

The API must never load untrusted codec/parser code into its own process. Spawn without a shell, use a fixed executable, construct arguments from allowlisted options, create a new process group, and capture bounded sanitized diagnostics. On stop, terminate the group, wait for a bounded grace period, then kill/reap it.

Production workers require:

- one constrained process/container security domain per session or small trusted pool;
- non-root identity, read-only root filesystem and private writable session directory;
- dropped capabilities, seccomp/AppArmor/Windows job-object equivalent and no Docker socket;
- protocol allowlist and disabled unsafe FFmpeg protocol chaining;
- CPU, memory, PID, open-file, disk, network and GPU quotas;
- signed/pinned media image, SBOM, vulnerability scanning and staged updates;
- node/site egress limited to approved camera/VMS destinations.

The lightweight P0.3 probe's destination validation is not automatically inherited by an independently spawned FFmpeg process. This PoC explicitly pins direct RTSP to the approved IP, but HTTP-family inputs and HLS-derived requests are not host-pinned. The production media path must either hand the worker a destination-pinned transport/credential proxy or enforce the approved IP, port and protocol set below the process with a firewall/egress proxy. HLS master/media playlists and key/map/segment URIs are derived network requests: each must be rejected, rewritten through a controlled fetcher or revalidated against the same policy before any fetch. Redirects and ambient proxy behavior must be disabled, and the fixed FFmpeg protocol whitelist must be regression-tested. This control must be demonstrated for IPv4, IPv6, DNS changes and multi-level playlists; application-level prevalidation alone is insufficient.

### Credential resolution and fail-closed external providers

P0.3 stores an encrypted opaque credential reference; it does not make that string a password. P0.3R now provides an encrypted, department-scoped local `credential-profile:<uuid>` resolver for controlled deployment and device qualification. The username and password are write-only through the API, encrypted as separate ciphertexts, validated again against the connection camera's department, and decrypted only during an assigned runtime start. `vault-ref:` and `kms-ref:` still require a workload-identity provider and fail closed when none is configured. No resolver may:

- treat the credential reference text as the credential;
- prompt interactively;
- fall back to a default password;
- log the reference or resolved value;
- persist the resolved value in runtime state/assets;
- launch a credentialed source when resolution is unavailable.

### Secret-in-argv risk

Passing `rtsp://user:password@host/...`, HTTP authorization headers, tokens or cookies in FFmpeg command arguments can expose them through process listings, crash diagnostics, monitoring agents or `/proc`. Therefore:

1. Embedded credentials remain rejected at onboarding.
2. P0.3R does not insert the decrypted endpoint into argv: it supplies a one-entry FFconcat manifest through protected stdin and uses `pipe:0` as the input argument. Query-token endpoints remain unsuitable for production until an enforcing proxy/handle boundary prevents disclosure through downstream library diagnostics and controls derived requests.
3. Prefer a short-lived local credential-injecting proxy/sidecar or an FFmpeg integration that reads protected material from a private inherited file descriptor/handle without logging it.
4. Any unavoidable platform-specific argv path is an explicit non-production compatibility mode, disabled by default, isolated under a dedicated OS identity, and visibly recorded as a security exception without recording the secret.
5. Environment variables are not a safe general replacement; privileged process inspection and crash collection may expose them.
6. Secret rotation revokes existing resolver leases and restarts affected sessions through the normal generation/state machine.

### Connection-kind eligibility

The standards runtime can start only a profile whose adapter yields an actual media input understood by the fixed runtime policy. Direct RTSP, HLS, MJPEG and controlled recorded-file profiles are eligible when their codec/mode and security checks pass.

An ONVIF device-service endpoint is not itself an RTSP media URI. The implemented Media1 negotiator obtains capabilities, profiles and an authorized stream URI before runtime handoff; every advertised HTTP/RTSP endpoint is revalidated by network policy, and the RTSP target is IP-pinned before credentials are applied. A generic `vms_http` base endpoint remains non-playable and fails closed until a tested vendor driver resolves a media URI. This remains materially narrower than a commercial native device pack.

Local encrypted credential profiles are an operational baseline, not final production secret custody. They share the configured federation data key and application process boundary. Production requires managed key custody or an external secret manager, workload identity, independent access audit, rotation/revocation propagation, and worker isolation. External references never fall back to the local database or treat their reference text as a password.

## 8. Codec and packaging policy

### H.264

If the source H.264 profile/level, audio and timing are compatible with the chosen HLS/browser target, prefer stream copy/remux. Remuxing minimizes latency, CPU/GPU use and quality loss. It still requires bounded parser/protocol handling and may need keyframe-aligned segments. **Current mismatch:** the PoC always invokes software `libx264`; it has no copy path or effective-mode field.

### H.265/HEVC

H.265 browser support is not assumed. The runtime chooses an explicit policy:

1. prefer a camera's H.264 substream for browser preview;
2. otherwise transcode H.265 to H.264 on a measured hardware/software path;
3. if no approved transcode capacity exists, fail with an honest codec-unsupported/capacity status rather than advertise a broken player.

The untouched primary H.265 source can later serve edge analytics or evidence workflows under their own contract. P0.3R preview transcoding must not silently change an evidence source or claim lossless output.

### Transcode controls

- declare input/output codec, resolution, FPS, bitrate and hardware acceleration in safe runtime metadata;
- bound scale/FPS/bitrate and reject operator-supplied arbitrary FFmpeg filters/options;
- detect NVDEC/NVENC, Intel QSV, VAAPI or other acceleration at worker readiness, then prove the exact path with a canary;
- use software fallback only within measured CPU budgets;
- monitor encoder session limits, GPU memory/utilization, thermal throttling and failure fallback;
- do not publish “streams per GPU” without a benchmark for the exact codec, resolution, FPS, GOP, filter graph and concurrent workload.

### Latency

Conventional HLS is not sub-second live video. End-to-end delay includes source GOP/keyframe interval, transport buffering, decode/transcode, segment duration, playlist depth, network and player buffer. Record measured glass-to-glass or source-timestamp-to-player latency with the complete configuration. Low-latency HLS/WebRTC is a later explicitly tested mode, not an implied result.

## 9. HLS asset authorization and filesystem safety

The media directory is private worker storage beneath the operator-configured `FEDERATION_RUNTIME_ROOT/<opaque-session-id>/`. The configured root is a server filesystem concern and is never returned to the browser. Nginx or another web server must not expose it as an unauthenticated static root.

### Request authorization

For every playlist/segment/key request:

- authenticate the user/service in production;
- authorize the runtime, connection, camera, department/district and requested action;
- require that the requested generation is current and not stopped/revoked;
- use an opaque runtime UUID and validated asset name, not a client-supplied filesystem path;
- avoid bearer tokens in query strings because browser history, referrers and access logs can leak them;
- audit playlist access at a useful rate while avoiding one audit row per segment storm.

The frozen API contract requires serving playlist and segments only through authenticated session routes. The observed implementation uses the broader platform's prototype actor header, which is not authentication. Therefore current media endpoints are suitable only for an isolated loopback evaluation and must not be described as production-authenticated or exposed to a shared network. Real feed use remains blocked until OIDC/service identity and camera-scoped authorization are enforced.

CORS, an unguessable UUID and a signed URL alone are not resource authorization. If short-lived signed capabilities are used, bind them to runtime, asset class, user/purpose and expiry, and support revocation.

### Traversal/symlink controls

- decode once under a canonical router contract; reject invalid/overlong encodings, NUL, slash, backslash, `..`, drive letters, UNC paths and Unicode separator/confusable forms;
- allow only runtime-generated manifest/segment filename patterns and extensions;
- resolve beneath the generation directory and open by trusted directory handle with no-follow semantics;
- reject symlink, junction, hard-link and reparse-point escape;
- never concatenate a route parameter onto a root and call a generic static-file helper without containment tests;
- cap range count/size and response bytes; emit fixed content types, not extension sniffing;
- revoke and delete stale generations only after active file handles/leases close.

### Cache policy

- media playlist: `Cache-Control: private, no-store` (or a measured very short private TTL);
- media segment: private bounded caching scoped to the authorized generation; immutable only if filenames are generation/sequence unique;
- include appropriate `Vary` behavior when authorization affects the representation;
- shared CDN/proxy caching is disabled unless cache keys include authorization scope and a security review proves no cross-user leakage;
- never cache an authorization error as a playable asset;
- HLS manifests contain only relative/authorized asset routes, never source URLs, credentials or worker paths.

Output storage is a rolling preview window. It is not archive retention. Supervisor cleanup has byte/time quotas and cannot delete outside its generation directory.

## 10. Capacity, bandwidth and GPU reasoning

### Per-session measurements

Record, rather than assume:

- source codec/profile, resolution, FPS, GOP and bitrate;
- media mode (copy/transcode), output bitrate and segment duration;
- input and egress bytes/sec;
- startup time, output freshness and reconnect time;
- process CPU/RSS/open files;
- GPU engine/memory/encoder-session use when applicable;
- preview viewers and delivered bytes;
- transient storage high-water mark.

Useful planning formulas:

```text
ingress bandwidth  ~= sum(active source bitrates) * protocol/measurement overhead
preview egress     ~= sum(output bitrate * concurrent viewers per session)
HLS rolling bytes  ~= output bitrate(bit/s) * retained seconds / 8
```

These are planning identities, not capacity proof. Add measured overhead, retransmission and headroom.

### Approximately 50-feed PoC

The PoC should qualify feeds in staged concurrency tiers (for example 1, 5, 10, 25, then 50 where hardware/network authorization permits), with a soak at each tier. Separate totals for:

- H.264 copy/remux sessions;
- H.265-to-H.264 transcodes;
- primary versus substream;
- simultaneously viewed previews;
- reconnect storm and cold-start recovery.

Fifty registered/onboarded feeds does not mean fifty simultaneous transcodes or viewers. Publish the exact achieved mix and limiting resource. Reserve headroom; do not size to a one-minute peak result.

### Approximately 80,000 cameras

Eighty thousand camera identities are not a single central FFmpeg pool. The scale target partitions by department, region, district, site/VMS and network reachability:

1. Central control plane retains global UUIDs, policy, scheduling intent and aggregate status.
2. Regional durable queues assign short leases to edge workers near the source network.
3. Site supervisors enforce local concurrency, bandwidth and reconnect budgets.
4. Most streams are off until viewed/processed; edge analytics use selected roles/FPS and send events centrally.
5. HLS preview remains regional/on-demand; central egress does not multiply every source continuously.
6. Worker images/adapters roll out by canary vendor/site and support fast rollback.
7. Failure domains prevent one site outage, codec bug or credential rotation from exhausting the state.

Capacity needs a measured placement model: compatible stream-copy slots, software transcode CPU, hardware encoder/decoder engines, GPU memory, site ingress, regional egress and transient disk. Kubernetes alone does not solve camera-network reachability, GPU session licensing or reconnect storms.

## 11. Failure modes and operator behavior

| Failure | Required detection | Runtime behavior | Safe operator evidence |
|---|---|---|---|
| invalid/retired/disabled profile | pre-start policy check | reject without spawning | stable policy code, connection UUID |
| credential resolver unavailable | fail-closed resolution | reject credentialed start | resolver-unavailable code; no reference/value |
| authentication rejected | sanitized FFmpeg/protocol classification | backoff then circuit per policy | `authentication_required`, attempt count |
| DNS/route/refused/timeout | pinned network/socket/process status | bounded reconnect | normalized network code and next retry |
| source reboot | process/output watchdog | reap, jitter, reconnect | detection and recovery timestamps |
| network loss/recovery | output freshness + process status | degraded/reconnecting/backoff | stale duration and recovered generation |
| stalled process with no output | manifest/segment/progress watchdog | terminate process group and retry | watchdog code and freshness age |
| malformed codec/stream | FFmpeg exit/progress classification | isolate process, circuit if repeated | safe codec error category |
| H.265 unsupported/no capacity | preflight/runtime capability check | select H.264 substream or fail honestly | requested/effective mode and capacity code |
| disk full/quota exceeded | storage watermark/write failure | stop/revoke/cleanup within scope | quota code and safe byte metrics |
| worker/API restart | reconciliation loop | adopt only verified generation or reap orphan | reconciliation action and generation |
| stop during start/backoff | generation-aware cancellation | cancel spawn/retry, reap, revoke | terminal `stopped` and stop time |
| password rotation | resolver lease/version change | revoke and restart generation | rotation-triggered restart, no secret |
| device clock drift | compare device/media/server times | retain server receive time and drift quality | drift measurement/clock-quality flag |

Raw FFmpeg stderr is diagnostic data available only in a restricted, redacted operational sink with tight retention. The browser receives stable categories and bounded messages.

## 12. Observability and reliability evidence

Minimum metrics, without endpoint/credential labels:

- desired/running/degraded/backoff/circuit-open sessions;
- starts, successful starts, exits and restarts by safe reason/adapter/region;
- startup and recovery duration histograms;
- output freshness age and stale-session count;
- watchdog/circuit transitions;
- active FFmpeg processes versus supervisor leases;
- input/output bitrate, transient disk, CPU/RSS, GPU engines/memory;
- HLS asset authorization denials and traversal attempts;
- queue age/concurrency budget at scale.

Logs carry request ID, runtime/connection/camera UUID, generation, transition, safe code and timing. They omit command line, source URI, DNS topology, credential reference/value, playlist content and authorization token.

Reliability claims require a stated observation window and denominator. Report starts attempted/succeeded, unexpected exits, reconnect success and recovery distribution. Never convert a small successful demo into “zero failure” or statewide availability.

## 13. P0.4 handoff

P0.4 may consume a supervised internal frame/packet handle or create its own authorized worker lease. It must not scrape browser HLS as the analytics source, retrieve a plaintext endpoint through a browser API, or duplicate credentials into an analytics database.

P0.3R runtime status can inform scheduling, but `running` means fresh media output under the runtime watchdog. It does not mean the image is useful for ANPR, the camera view is correct, timestamps are trustworthy, or model inference is healthy. P0.4 owns those separate quality dimensions.

## 14. Implementation and claim gate

P0.3R may be presented as implemented only when:

- frozen API route, field and state names match OpenAPI and frontend types;
- start/status/stop are generation-safe and idempotent;
- process spawn uses no shell and stop reaps the process group;
- every network/worker deadline and retry parameter is bounded;
- watchdog freshness, jittered backoff and circuit-open/half-open behavior have deterministic tests;
