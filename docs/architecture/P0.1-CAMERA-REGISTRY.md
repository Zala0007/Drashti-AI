# P0.1 Camera Registry — Architecture and Acceptance Gate

Status: implementation baseline for the Drishti AI P0.1 module.

## 1. Purpose

The registry is Drishti AI's authoritative inventory and discovery layer. It answers:

- Which department owns a camera?
- Where is it located?
- What type and capabilities does it advertise?
- Is it active, retired, online, degraded, offline, or not yet observed?
- Which safe references will a future federation adapter use?
- Who changed metadata, and when?

The registry does not transport, decode, record, or analyze video. Keeping that boundary explicit prevents a foundational metadata service from becoming a credential store or vendor-coupled VMS.

## 2. Relationship to the hybrid architecture

P0.1 implements the Model 1 foundation within Drishti's selected hybrid architecture:

This separation follows the program principle: integrate existing infrastructure, process intelligently at the edge, and correlate intelligence centrally. P0.1 is a control-plane service; it does not justify continuously centralizing video.

## 3. Components

### 3.1 Registry API

A versioned FastAPI service exposes department and camera operations beneath `/api/v1`. Input models reject unknown or invalid values, persistent identities use UUIDs, and database access is isolated from transport models.

### 3.2 Operator UI and GIS

The P0.1 frontend consumes the API rather than maintaining a parallel data model. It provides inventory search/filtering, camera details, onboarding, operational counts, and a map sourced from the GeoJSON endpoint. Coordinates remain WGS 84 (`EPSG:4326`) at the API boundary for browser interoperability.

### 3.3 Database profiles

| Profile | Intended use | Geospatial behavior | Limitations |
|---|---|---|---|
| PostgreSQL + PostGIS | shared, staging, production-shaped deployment | native point geometry and spatial indexing/methods | requires managed database operations and tested migrations |
| SQLite | single-developer, no-Docker fallback | latitude/longitude filtering and application-produced GeoJSON | no PostGIS equivalence, no multi-node writes, no production HA |

PostGIS is the architectural source of truth for statewide operations. SQLite exists so a contributor can exercise the P0.1 workflow on a constrained workstation; it must not become a silent production default.

### 3.4 Audit history

Metadata mutations produce append-oriented audit entries containing the affected entity, action, timestamp, and safe before/after context. Audit records must not include a camera password, token, full credential-bearing URI, or secret value. Actor identity is limited until the authentication/RBAC module is implemented; that limitation must remain visible rather than being represented as verified attribution.

## 4. Domain model and invariants

### Department

A department provides the administrative scope for cameras. Its code is stable and unique; its display name may evolve.

### Camera

Every camera has:

- an immutable UUID for internal and cross-service references;
- a human-readable camera code unique within the registry;
- a department relationship;
- a name and geographic placement;
- lifecycle status and operational health as separate dimensions;
- optional vendor, model, VMS, connectivity, capability, ownership, storage, installation, and tagging metadata;
- optional **opaque**, non-secret integration references.

Required creation fields are `camera_code`, `camera_name`, `department_id`, `district`, `latitude`, and `longitude`.

Important invariants:

- latitude is in `[-90, 90]`; longitude is in `[-180, 180]`;
- lifecycle status is one of `planned`, `active`, `maintenance`, `inactive`, `retired`;
- health is one of `online`, `offline`, `degraded`, `unknown`;
- lifecycle and health are not interchangeable: a maintenance camera may still answer a heartbeat;
- retirement is explicit and non-destructive so evidence references and audit history remain stable;
- a heartbeat updates operational state but must not rewrite ownership or physical metadata;
- capability claims describe configuration/advertisement, not a measured guarantee;
- timestamps are emitted in UTC ISO 8601 form.

## 5. Credential and sensitive-data boundary

### Allowed registry content

- vendor/model names and advertised protocol capabilities;
- sanitized stream type such as `rtsp`, `onvif`, `hls`, or `vendor_api`;
- non-secret network/connectivity classification;
- an opaque `stream_reference` naming a future connection profile;
- an opaque `credential_reference` naming an external secret record;
- department, location, health, and maintenance metadata according to authorization policy.

### Forbidden registry content

- usernames, passwords, API keys, private keys, bearer tokens, or session cookies;
- URLs of the form `rtsp://user:password@host/...`;
- secrets in camera names, tags, notes, import files, API error messages, audit diffs, or logs;
- unencrypted vendor configuration dumps;
- production feed addresses in public demo seed data.

### Future resolution flow

```text
authorized adapter worker
        |
        | camera UUID
        v
registry -> safe stream_reference + credential_reference
        |
        +------> connection-profile service (restricted endpoint/topology)
        |
        +------> secret manager (credential material, short-lived access)
```

The browser never receives credential material. The adapter must resolve secrets server-side using workload identity and least privilege. Secret rotation must not require editing camera metadata.

## 6. Threat-aware design review

| Threat | P0.1 treatment | Required hardening beyond P0.1 |
|---|---|---|
| Credential disclosure through metadata/imports | secret fields are outside the camera contract; sample data is sanitized | import content inspection, vault integration, secret scanning |
| Unauthorized inventory enumeration | deployment is explicitly restricted to a trusted development/internal network | OIDC authentication, department/district ABAC/RBAC, API gateway policy |
| IDOR across departments | UUIDs are not treated as authorization | resource-scoped authorization on every read/write |
| Tampering with camera location/status | validation plus audit history | authenticated actor attribution, approvals for sensitive changes, tamper-evident audit export |
| CSV formula injection | imports are treated as data; exports must neutralize spreadsheet formula prefixes | security tests on import/export implementations |
| CSV/JSON resource exhaustion | bounded files, rows, field lengths, and request bodies are required | gateway/body limits and measured bulk-job quotas |
| Stored XSS in labels/tags | API stores plain data; UI must render as text | CSP and automated UI security tests |
| SSRF through a future stream address | P0.1 does not initiate stream connections | egress allowlists, endpoint validation, DNS/IP protections in adapters |
| Sensitive topology leakage in logs/backups | log only safe identifiers and protect database artifacts | centralized access policy, encryption, retention and tested restore controls |
| Audit-log erasure | operational mutation history is append-oriented | separate immutable/WORM or cryptographically chained audit sink |

**Security status:** P0.1 authentication and authorization are not implemented. The service is suitable only for isolated local demonstration or a protected internal evaluation network until that gate is closed. CORS is not an access-control mechanism.

## 7. Operational behavior

### Camera onboarding

1. An operator or trusted integration creates/selects a department.
2. The camera payload or CSV is validated against the canonical schema.
3. Duplicate codes, invalid foreign keys, coordinates, or enums are rejected without silently changing data.
4. The camera receives a UUID and initial audit entry.
5. The camera becomes available to list, details, statistics, and GeoJSON views.

Bulk import must return actionable row-level outcomes. Whether the operation is atomic or partial must be stable and documented by the API implementation; callers must never infer success only from HTTP transport status.

### Heartbeat

Heartbeat is an operational signal, not proof that video is usable. P0.1 records the stated health and last-seen time. Frame-freeze, FPS, latency, authentication failures, and reconnect behavior belong to the stream-health module after an adapter can measure them.

### Retirement

Retirement is preferred to physical deletion. A retired camera remains addressable for audit and future event/evidence referential integrity, but downstream services must exclude it from new assignments by default.

## 8. Scale path

The 50-feed evaluation and 80,000-camera target affect design even though P0.1 is metadata-only:

- use database-side filters and pagination rather than loading the entire registry into a browser;
- index unique camera code, department, district, lifecycle, health, and geospatial columns according to measured queries;
- use GeoJSON bounding-box/zoom queries or vector/cluster aggregation before statewide maps become dense;
- keep API replicas stateless and place PostgreSQL behind managed HA/connection pooling for production;
- move large imports to bounded background jobs when synchronous latency becomes unacceptable;
- retain stable UUIDs across adapters, detections, alerts, and evidence;
- measure API latency and query plans with representative cardinality before publishing capacity claims.

P0.1 makes no unverified throughput or availability claim. Load, failover, backup, recovery-time, and recovery-point figures require a measured deployment report.

## 9. Acceptance criteria

P0.1 is complete only when all applicable checks are evidenced:

### Functional

- Create and list departments.
- Create, list, filter, retrieve, and update cameras.
- Reject invalid coordinates, enums, missing departments, and duplicate camera codes with useful errors.
- Retire a camera without physical deletion.
- Record a heartbeat and expose the resulting health/last-heartbeat state.
- Import the representative CSV and return row-level results.
- Produce valid GeoJSON for authorized registry cameras.
- Produce camera statistics without requiring the UI to count the full dataset.
- Return chronological audit history for camera metadata actions.
- Complete the same core API flow against SQLite and PostgreSQL/PostGIS, noting intentional geospatial differences.

### User flow

- Operator can view inventory and summary health.
- Operator can filter cameras and inspect a camera record.
- Operator can onboard a camera with validated coordinates.
- Operator can see cameras on the GIS view and distinguish health states.
- Loading/error/empty states are understandable on a laptop and presentation display.

### Security and operations

- No credential material exists in schema, seeds, API examples, browser payloads, logs, or audit output.
- Service documentation clearly warns that P0.1 has no authentication/RBAC.
- Health endpoints and structured request logs are available; deployment commands
  disable Uvicorn's query-bearing access log in favor of the sanitized application log.
- Configuration is externalized and `.env` is ignored.
- Database data uses a persistent volume in the Compose profile.
- Automated backend/frontend tests and the exact manual demonstration flow pass in the target environment.
- The API contract and screenshots/demo describe observed behavior only.

The commands and evidence checklist are in `docs/deployment/P0.1-LOCAL.md`. A command appearing there is not itself proof that it was executed.

## 10. Explicit next-module boundaries

### P0.2 — GIS Operations

P0.2 turns the registry's safe metadata, statistics, and GeoJSON into the Command Centre and dedicated GIS Operations workspace. It owns camera search/filter/focus/details, non-color health cues, marker clustering, and a reusable route presentation layer that remains empty until a real event-correlation service exists. See `docs/architecture/P0.2-GIS-OPERATIONS.md`.

It does not ingest streams, run ANPR, generate alerts, or infer routes.

### P0.3 — Federation and stream onboarding

Owns:

- common adapter interface (`connect`, `disconnect`, `health_check`, `get_stream`, `get_metadata`, `discover_cameras`, `get_camera_status`);
- RTSP, ONVIF, recorded/simulated feed, and vendor-VMS adapter implementations;
- restricted connection profiles and server-side secret resolution;
- endpoint validation, SSRF protection, reconnect/backoff, and measured stream health;
- on-demand stream handles consumed by authorized workers.

Does not rewrite P0.1 camera identity or store vendor secrets in the registry.

### Later P0 modules

- live-view gateway and browser-safe delivery;
- edge vehicle/plate detection, tracking, OCR, and event normalization;
- registration search and cross-camera route reconstruction;
- watchlist matching and real-time alert lifecycle;
- evidence storage and retention.

### P1 security/operations gates

Authentication, resource-scoped RBAC/ABAC, fully attributed tamper-resistant audit, observability, backup/restore, offline edge buffering, and formal retention controls are required before production exposure. Some must be pulled forward before connecting any real government feed, even if their roadmap label is P1.
