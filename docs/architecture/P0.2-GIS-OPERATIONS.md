# P0.2 GIS Operations — Architecture and Current Boundary

Status: current implementation baseline built on the completed P0.1 Camera Registry.

## 1. Purpose

GIS Operations converts the registry's normalized camera metadata into an operational geospatial view. It lets an operator answer which registered cameras exist in an area, which department owns them, what lifecycle and health state they report, and which declared VMS or analytics capabilities they carry.

P0.2 is a metadata control-plane module. It does not open a camera stream, validate video quality, detect a plate, match a watchlist, create an alert, or infer a vehicle route.

## 2. Implemented scope

The current frontend provides three working surfaces:

- **Command Centre:** an entry view using live registry statistics and mapped-camera data to summarize the inventory and direct operators to GIS or registry workflows.
- **GIS Operations:** a larger map workspace for finding, filtering, focusing, and inspecting registered cameras.
- **Camera Registry:** the P0.1 inventory, onboarding, import, health, detail, and audit workflows.

The GIS implementation currently includes:

- camera coordinates read from the registry GeoJSON endpoint rather than a separate browser dataset;
- API-backed inventory statistics and filter options;
- search across safe camera and location metadata;
- department, district, city, lifecycle, health, vendor, VMS, and declared AI-capability filters;
- automatic map focus when an operator selects a camera;
- marker clustering to keep dense views usable;
- marker health encoded with both color and a glyph, so status is not communicated by color alone;
- camera detail access from map/list selection, including identity, ownership, location, lifecycle, health, integration metadata, and declared capabilities where present;
- explicit loading, empty, unavailable, and retry states;
- a reusable route-overlay component that accepts ordered, timestamped camera-event points when a future correlation service supplies them.

No sample alert, detection, ANPR count, or vehicle path is presented as live data. Planned intelligence modules remain labelled as unavailable or pending.

## 3. Data and component flow

```text
PostgreSQL/PostGIS (production target) or SQLite (local fallback)
                              |
                              v
                    P0.1 Registry API
             list + statistics + filter options
                       + GeoJSON cameras
                              |
                              v
               React application data state
                   /          |          \
                  v           v           v
         Command Centre   GIS Operations   Registry
                              |
                    Leaflet marker clusters
                    + selection/focus/details
                    + empty route overlay hook
```

WGS 84 coordinates (`EPSG:4326`) remain the browser-facing boundary. Database-side filtering is authoritative; the UI debounces free-text input and refreshes list, statistics, and GeoJSON from the same filter state so the views describe the same selection.

Map tiles are visual context, not registry data. Their provider URL and attribution are configurable. A production deployment must use an approved tile service or an internally hosted tile stack whose availability and data-handling terms meet government requirements.

## 4. Status and accessibility cues

Camera health is represented as `online`, `degraded`, `offline`, or `unknown`. Each map marker and legend entry combines a distinct glyph with its color treatment. Text labels and detail views provide the full status. Lifecycle (`planned`, `active`, `maintenance`, `inactive`, or `retired`) remains a separate property and filter.

The GIS must not interpret a stored heartbeat as proof that usable video exists. Stream reachability, decode success, frame freshness, FPS, and inference health become measurable only after P0.3 provides an authorized adapter and stream-health contract.

## 5. Search, filtering, and focus

Search and filters operate on normalized registry metadata. The implemented filters cover department, district, city, lifecycle, health, vendor, VMS, and declared AI capability. Selecting a matching camera focuses the map and opens the same canonical camera record used by Registry; the map does not maintain a competing identity model.

Filter-option values are derived from stored, non-secret camera metadata. They must never expose credentials, credential-bearing URLs, private endpoints, or other connection topology that belongs to the future restricted connection-profile service.

## 6. Route and alert visualization boundary

The map contains a reusable route layer with an input contract for ordered camera points and optional observation timestamps. It is intentionally empty today. The layer is presentation infrastructure, not route intelligence, and its existence is not evidence that a vehicle has been detected or correlated.

A later cross-camera correlation service should provide a route only from durable, authorized events containing at least:

- a stable event and camera UUID;
- normalized entity identity and confidence;
- observation time with clock-quality context;
- camera coordinates resolved from the registry;
- provenance for the model, source, and watchlist/correlation decision.

Future alert markers should use a separate event layer and query boundary, be distinguishable from camera health, support severity and acknowledgement state, and link to authorized evidence. They must not be synthesized from camera metadata or displayed before the alert lifecycle is implemented.

## 7. Scale boundary and 80,000-camera path

The present GeoJSON endpoint and browser-side Leaflet clustering are an appropriate baseline for the hackathon dataset and development datasets up to the current API ceiling of approximately 10,000 returned camera features. That ceiling is a payload and rendering guardrail, not a claim that one browser should load the statewide 80,000-camera estate at once.

The statewide path is progressive and does not require replacing camera identity or the operator workflow:

1. Add bounding-box and zoom parameters so the API returns only features relevant to the current viewport.
2. Add database-side spatial filtering using PostGIS indexes and measured query plans.
3. Return server-computed clusters at low zoom levels and individual cameras only when the viewport is sufficiently narrow.
4. Move dense map delivery to cached vector tiles where measurements show GeoJSON payload or DOM/Leaflet work is the bottleneck.
5. Keep list endpoints paginated and statistics aggregated in the database rather than derived from all browser features.
6. Cache safe, slow-changing filter options and invalidate them when registry metadata changes.
7. Load event, alert, and route layers independently so a failure or high event volume cannot block the base camera inventory.

Capacity, latency, concurrency, and availability figures require a repeatable load test with representative distribution and are not asserted by this baseline.

## 8. Security and operational constraints

- The browser receives safe registry metadata only; it does not receive credentials or resolve stream endpoints.
- P0.1/P0.2 authentication and resource-scoped authorization are not yet implemented. Use only an isolated local demonstration or protected internal evaluation network.
- Camera locations and ownership metadata can still be sensitive. Protect API access, logs, exports, screenshots, tiles, and database backups accordingly.
- External tile requests may disclose approximate viewed areas to the tile provider. Production must use an approved network and tile architecture.
- Map popups and details render registry values as text; future rich evidence content requires its own content-security review.
- Route and alert layers must enforce the same department/district/case authorization as their source events when those services are introduced.

## 9. Current exclusions

The following are not implemented in P0.2:

- live or recorded video viewing;
- NVR, VMS, RTSP, or ONVIF connectivity;
- stream-health measurement;
- object or vehicle detection;
- number-plate recognition or OCR;
- face recognition;
- watchlist matching;
- real-time alert creation, acknowledgement, or notification;
- cross-camera association or route inference;
- event/evidence storage;
- authentication, RBAC, or ABAC.

## 10. Next module: P0.3 Stream Onboarding / Federation Adapter

P0.3 owns vendor-isolated adapters, restricted connection profiles, secret-manager resolution, endpoint validation and SSRF controls, reconnect/backoff behavior, and measured stream health. It consumes the stable camera UUID and safe capability metadata from P0.1; it does not put vendor secrets or raw feed endpoints into GIS state.

Only after that boundary is operational should browser-safe live viewing and edge analytics feed real detections into the future alert and route layers.
