# P0.3 Stream Onboarding and Federation Adapter

Status: current P0.3 implementation baseline, with production gates explicitly separated below.

This document distinguishes three kinds of statements:

- **Implementation baseline** describes behavior that must be confirmed by code and automated tests in this repository before a demo claim is made.
- **Production requirement** describes a mandatory control for real government feeds, even when the local proof of concept cannot fully exercise it.
- **P0.4 boundary** describes functionality intentionally excluded from P0.3.

## 1. Purpose

P0.3 is Drishti AI's vendor-neutral federation control plane. It onboards a safe connection profile, selects an adapter, performs a bounded lightweight connectivity probe, and returns normalized health and capability metadata without disclosing the raw endpoint or credential reference.

The module is the bridge between the P0.1 camera identity/GIS foundation and later stream-processing services. It preserves departmental VMS ownership instead of requiring every camera to be replaced or continuously recorded at the centre.

P0.3 must answer:

- Which adapter class can represent this source?
- Is the supplied configuration structurally valid and its protected connection material handled safely?
- Is the source endpoint permitted by explicit network policy?
- Can an authorized server-side worker make a bounded protocol handshake?
- What safe capability and latency information can an operator inspect?
- Which actor requested, changed, enabled, disabled, or probed the profile?

## 2. Scope and non-goals

### P0.3 implementation baseline

- adapter descriptors for RTSP, HLS, MJPEG, ONVIF, generic VMS HTTP reachability, and a controlled recorded-file source;
- create, retrieve, list, update, enable/disable, and probe workflows for connection profiles;
- application-layer encryption for protected connection material at rest;
- opaque linkage to a P0.1 camera and, where applicable, a credential held outside the registry;
- explicit private-network CIDR allowlisting before any network probe;
- bounded lightweight probes that do not continuously decode or relay video;
- normalized, non-secret probe metadata and error categories;
- audit records for material profile and probe actions;
- a UI workflow that never receives a stored endpoint or credential reference after submission.

### Explicit non-goals

P0.3 does **not** claim:

- browser live view, WebRTC/HLS transcoding, or central video relay;
- continuous frame decoding, recording, clip extraction, or evidence retention;
- ANPR, facial recognition, detection, tracking, watchlist matching, alerts, or route reconstruction;
- full vendor SDK coverage merely because a generic VMS adapter descriptor exists;
- ONVIF discovery across arbitrary networks;
- production authentication, authorization, high availability, or certified capacity unless separately evidenced.

These exclusions are intentional. A successful protocol handshake is not proof that frames are fresh, decodable, authorized for display, or suitable for AI.

## 3. Position in the hybrid architecture

The following is the deployable target shape. The current evaluation baseline runs the orchestrator/adapters synchronously inside the API process.

```text
                              CONTROL PLANE

  P0.1 Registry/GIS       P0.3 Federation API       Audit/operations
  camera UUID + safe ---> connection profile -----> safe action history
  source metadata          adapter assignment        health summary
                                  |
                                  | encrypted endpoint envelope
                                  | + opaque credential reference
                                  v
                         Probe orchestrator
                                  |
                    validate policy before dispatch
                                  |
                 +----------------+----------------+
                 |                                 |
                 v                                 v
        Edge adapter worker                Central adapter worker
        site/VMS network                    approved central path
                 |                                 |
                 +---------- bounded probe --------+
                                  |
                                  v
                  Department camera / NVR / VMS

                              DATA PLANE (P0.4+)

  Authorized stream worker -> decode/relay/inference -> normalized events
```

The control plane stores configuration and observations. It does not become the video data plane. An edge adapter can be placed inside a department network so the central platform receives normalized health/events rather than requiring unrestricted inbound access to every camera subnet.

## 4. Component responsibilities

### 4.1 Federation API

The versioned API accepts validated profile commands and returns only normalized, safe response models. Unknown fields are rejected. Profile identity is an immutable UUID and is separate from the referenced P0.1 camera UUID.

The API is responsible for:

- validating adapter type and adapter-specific non-secret options;
- enforcing profile lifecycle invariants;
- encrypting protected connection material before persistence;
- redacting protected fields from every read, error, audit, and log path;
- applying network policy before dispatching a probe;
- recording an audit action and safe probe summary.

A UUID is not authorization. **Production requirement:** every operation must be authenticated and scoped by department, district, camera, and role before any real feed is connected.

### 4.2 Connection-profile store

A connection profile belongs to one registered camera and names one adapter type. The profile may contain:

- a human-readable, non-secret label;
- adapter type and enabled/disabled state;
- an encrypted endpoint/configuration envelope;
- an encrypted or otherwise protected opaque credential reference;
- the latest normalized probe summary;
- creation/update timestamps.

The raw endpoint and credential reference are write-only at the API boundary. They must not appear in list/detail/probe responses, logs, exception text, metrics labels, traces, frontend state persisted to storage, or audit diffs.

The database ciphertext, nonce/IV, algorithm/version marker, and key identifier are not themselves sufficient to decrypt a profile. The master key is supplied from process configuration for the local baseline and from a managed KMS/HSM or secret manager in production.

### 4.3 Adapter plugin boundary

Each adapter implements the same narrow contract:

1. declare a stable adapter type and safe capability descriptor;
2. validate scheme, syntax and address policy before making a protocol connection (hostname validation performs DNS resolution);
3. accept a short-lived resolved profile inside the worker boundary;
4. execute a bounded probe;
5. return normalized metadata or a normalized failure category;
6. dispose of plaintext connection material after the operation.

Adapters must not receive database sessions, global application settings, arbitrary filesystem access, or permission to select their own network target. The orchestrator supplies the already validated target and deadline.

**Implementation baseline:** in-process adapter isolation is a software boundary, not a hostile-code sandbox.

**Production requirement:** vendor SDK adapters run out of process in a dedicated container or edge service with a read-only root filesystem, non-root identity, dropped Linux capabilities, seccomp/AppArmor policy, explicit CPU/memory/time limits, and network egress limited to approved camera/VMS ranges. A plugin crash or hang must not take down the federation API.

### 4.4 Network-policy validator

The validator canonicalizes the endpoint, rejects embedded credentials, resolves hostnames, and evaluates every resolved address. Public unicast targets are permitted by the evaluation baseline after scheme and prohibited-address checks. Private and loopback targets are permitted only when every resolved address falls inside an explicitly configured CIDR.

There is no implicit `allow all private ranges` behavior. An operator must configure the exact private/loopback CIDR ranges required for the demonstration environment. Link-local, multicast, unspecified, reserved, and known cloud-metadata addresses remain denied. Public-unicast support exists for government-provided evaluation feeds; it is not a general internet-egress approval.

The implemented network adapters connect directly to a policy-approved resolved IP. HTTP-family adapters preserve the hostname only for the `Host` header and TLS SNI, disable redirects, and do not inherit proxy configuration; RTSP also connects to a validated IP. This closes the validation/use DNS-rebinding gap in the current adapters. **Production requirement:** enforce the same destination policy through a firewall or controlled egress proxy so a future or compromised adapter cannot bypass the application boundary.

### 4.5 Probe orchestrator

The orchestrator performs a finite, deadline-bound operation. It does not keep a stream open after recording the probe result. It normalizes adapter-specific results into fields suitable for comparison and operations.

A probe result can safely report:

- result category and observation time;
- adapter type and selected safe transport descriptor;
- elapsed latency;
- protocol handshake result;
- sanitized media/capability metadata limited to the normalized vocabulary;
- a stable non-secret error code;
- adapter kind; its version and declared capabilities remain available through the manifest endpoint.

Probe metadata must not report the raw endpoint, path/query, username, credential reference, response headers containing secrets, vendor payload dumps, or exception messages copied directly from third-party libraries. The profile response may carry only the separately defined sanitized endpoint display.

### 4.6 Audit

Material actions are append-oriented: profile create/update, enable, disable, and completed probe outcome. Audit contains safe identifiers, actor attribution when authentication exists, request ID, action, time, and redacted before/after context.

**Implementation baseline:** locally supplied actor headers are demonstration attribution only and must not be represented as verified identity.

**Production requirement:** identity comes from validated OIDC/service credentials; audit is exported to a tamper-resistant sink with retention and access controls separate from the application database.

## 5. Adapter classes and probe semantics

| Adapter class | Lightweight P0.3 behavior | Does not prove |
|---|---|---|
| RTSP | Parse, authorize and pin the target; make a bounded RTSP `OPTIONS` handshake and normalize response status | session/media description, continuous decode, frame freshness, visual quality, recording, AI suitability |
| HLS | Authorize and pin the playlist target; validate HTTP status/content type and at most a 4 KiB prefix beginning with `#EXTM3U`; do not follow segment/key URIs | complete playlist correctness, segment continuity, playback, latency target, DRM/decryption, browser delivery |
| MJPEG | Authorize and pin the HTTP target; validate bounded HTTP status and multipart/JPEG content-type headers without retaining frames | sustained multipart decode, frame rate, visual quality |
| ONVIF | Authorize and pin a configured device-service endpoint; issue a bounded `GetSystemDateAndTime` SOAP request and normalize its HTTP result without parsing response XML | unrestricted network discovery, device identity/capability parsing, profile-stream validation, PTZ control |
| Generic VMS HTTP (`vms_http`) | Validate and pin a base endpoint and return generic HTTP reachability metadata | compatibility with every VMS/SDK or camera behind it |
| Recorded file | Validate an application-controlled staged artifact reference and safe media descriptor; no arbitrary host path is accepted | upload security, long-running playback, decode, analytics |

Capability descriptors are declarations about the adapter implementation, not observations about a particular camera. Probe observations and configured capabilities remain separate.

## 6. Profile lifecycle

The implemented lifecycle is intentionally small:

```text
create enabled -> unverified -> probe -> reachable
                         |          |--> unreachable
                         |          |--> authentication_required
                         |          |--> blocked
                         |          |--> misconfigured
                         |          `--> adapter_unavailable
                         |
                         `-- disable -> disabled
                                           |
                                           `-- enable -> unverified
```

Changing the endpoint or adapter resets an enabled profile to `unverified`; disabling sets `disabled`; enabling returns it to `unverified`. A failed probe does not delete configuration, rewrite camera health in P0.1, or imply permanent failure. Enabling a profile does not start continuous streaming in P0.3.

## 7. Secret and topology handling

### Browser/API boundary

- Endpoint and credential reference are accepted only over an authenticated TLS-protected write operation in production.
- Read models expose booleans such as whether protected configuration exists, not the value itself.
- Update semantics distinguish omitted (retain) from explicit replacement; plaintext is never returned for confirmation.
- Validation errors identify the field category without echoing its value.
- The UI clears protected inputs immediately after submission and does not place them in URL state, analytics, local storage, or error telemetry.

### Worker boundary

- Decrypt only immediately before a probe.
- Resolve a credential reference only inside an authorized worker using workload identity.
- Keep plaintext in memory for the shortest practical lifetime.
- Do not pass plaintext on a command line or environment variable to a child process.
- Apply redaction to third-party library logs and disable verbose protocol logging in shared environments.

The current probes do not resolve or apply credential material; they may return `authentication_required`. Secret-manager resolution is part of the authorized internal handoff/worker boundary and must not be inferred from the presence of an encrypted reference.

### Persistence and backups

- Application-layer encrypted values remain encrypted in database backups.
- Key material is backed up independently under dual control; never store the only recovery key beside the database backup.
- Restore testing must demonstrate both authorized decryptability and inability to decrypt with a retired/unauthorized key.

## 8. Reliability and failure isolation

The implementation baseline gives every synchronous network probe one monotonic total deadline across resolved-address attempts, confines recorded-file inspection to local metadata beneath the media root, normalizes adapter failures into stable codes, and records an observation without creating another profile. It does not yet provide a durable queue, automatic retry scheduler, circuit breaker, or separate worker bulkhead.

Production operation requires bounded jittered retries, global and per-site concurrency limits, circuit breakers, persisted idempotent jobs, worker liveness/readiness, queue-depth/latency metrics without endpoint labels, and monitored clock synchronization. Operator-triggered probes must not create an unbounded storm.

## 9. Deployment topology

### Evaluation: approximately 50 feeds

- one protected federation API instance;
- PostgreSQL/PostGIS for registry and profile metadata;
- synchronous deadline-bounded probes in the API process for the current baseline; a separate bounded worker pool is the recommended next operational step;
- adapters selected per supplied feed type;
- exact explicit CIDRs for private/loopback targets and the documented public-unicast evaluation policy;
- no continuous decoding by P0.3;
- structured safe logs and audit evidence.

This topology is a functional proof, not an HA or statewide capacity claim.

### Statewide path: approximately 80,000 cameras

1. Partition operational ownership by region, department, and site while retaining stable global UUIDs.
2. Place edge federation workers near departmental VMS/camera networks; prohibit broad camera-network access from the public/central tier.
3. Dispatch probe jobs through a durable regional queue and enforce per-site concurrency/rate budgets.
4. Keep the central service stateless; use HA PostgreSQL, connection pooling, read replicas for inventory, and partitioned observation/audit storage based on measured queries.
5. Export normalized health/capability events rather than polling all cameras from one central process.
6. Use versioned adapter images and staged rollout/canaries per vendor or region.
7. Measure handshake latency, success rate, worker saturation, queue age, and failure recovery with representative protocols before publishing sizing numbers.

At scale, `80,000 cameras` is an inventory cardinality, not a claim that 80,000 video feeds are centrally decoded at once. Decode/inference capacity is sized in P0.4 from codec, resolution, FPS, model, batching, GPU, and required concurrency.

## 10. Production security and operations gate

Before any real government endpoint is onboarded:

- OIDC authentication and department/camera-scoped RBAC/ABAC are enforced;
- TLS/mTLS and workload identity protect service-to-service calls;
- KMS/HSM-backed envelope encryption and secret-manager resolution replace local key handling;
- adapter egress is enforced by network policy/firewall as well as application validation;
- DNS resolver behavior, redirect policy, proxy environment, and IPv4/IPv6 bypass cases are tested;
- vendor adapters are isolated out of process and supply-chain scanned/signed;
- database HA, encrypted backups, restore, RPO/RTO, and key-recovery drills are evidenced;
- logs/audit/metrics are centralized, redacted, access controlled, and retained by approved policy;
- rate limits, quotas, job backpressure, circuit breakers, and incident runbooks are tested;
- data classification, lawful access, camera-owner approvals, and topology-disclosure controls are signed off.

## 11. P0.4 boundary

P0.4 consumes an authorized connection profile through a server-side, short-lived handle. It owns sustained connection supervision, decode/transcode where required, browser-safe live viewing, frame freshness/FPS measurements, edge inference, and normalized detection events.

P0.4 must not request plaintext endpoints through a browser-facing P0.3 read API or duplicate credentials into its own database. It receives only the authorization and material required for its assigned workload, with auditable lease and expiry semantics.

## 12. Acceptance evidence

P0.3 is complete only when repository evidence confirms:

- all six adapter classes are listed through the implemented adapter-discovery contract;
- profile CRUD/lifecycle behavior uses the frozen API schema;
- protected fields are encrypted in storage and absent from every response, audit entry, log, and error;
- invalid schemes, embedded credentials, link-local/multicast/unspecified/reserved/metadata targets, and non-allowlisted private or loopback addresses are rejected; tested public-unicast behavior matches the documented evaluation policy;
- adapters connect to validated resolved IPs and disable redirect/proxy bypasses; production evidence additionally covers firewall/egress enforcement;
- every network probe is total-deadline-bound, recorded-file inspection is confined to safe local metadata, and all results use normalized safe fields;
- profile and probe audit actions are recorded without protected content;
- tests cover encryption failure, missing/wrong key, redaction, policy bypasses, timeouts, and adapter error normalization;
- the UI demonstrates onboarding and safe probe status without claiming live view or AI;
- exact verification commands, environment profile, timestamp, and results are captured for submission evidence.

This document is not itself proof that those checks passed. The implementation and generated OpenAPI contract are authoritative once frozen.
