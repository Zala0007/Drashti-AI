# P0.1 Local and Container Deployment

This runbook covers the Camera Registry module only. It provides a no-Docker SQLite workflow for fast development and a production-shaped Compose workflow using PostgreSQL/PostGIS.

## 1. Prerequisites

### No-Docker path

- Python 3.11 or newer
- Node.js 20 LTS or newer and npm
- PowerShell 7 is recommended on Windows

### Container path

- Docker Engine/Desktop with Compose v2
- loopback ports `5173` and `8000` available, or adjusted in local configuration

Docker is optional for local feature work. It is required to exercise the supplied PostGIS container profile.

## 2. Configuration

For Compose, create a root environment file:

```powershell
Copy-Item .env.example .env
```

`.env` is ignored by Git. The example contains development placeholders, not deployable credentials. Do not add camera secrets, credential-bearing URLs, or government feed endpoints to this file. A later adapter module will resolve camera credentials from a secret manager.

Docker Compose reads the root `.env` automatically. The Python service reads process environment variables; plain `uvicorn` does not automatically load the root file. The local defaults already select SQLite. Set an override explicitly in PowerShell when needed, for example:

```powershell
$env:DATABASE_URL = "sqlite:///./drishti_registry.db"
$env:CORS_ORIGINS = "http://localhost:5173"
```

Relevant backend settings:

| Setting | Local default | Notes |
|---|---|---|
| `APP_ENV` | `development` | environment label; does not itself enforce security |
| `API_V1_PREFIX` | `/api/v1` | stable API namespace |
| `DATABASE_URL` | SQLite URL | no-Docker developer profile |
| `AUTO_CREATE_SCHEMA` | `true` | convenience for local SQLite only |
| `DB_ECHO` | `false` | avoid verbose SQL and topology leakage |
| `CORS_ORIGINS` | local Vite origins | CORS is not authorization |
| `VITE_API_BASE_URL` | `/api/v1` | compiled into the browser; same-origin/proxied by default and must never contain a secret |

For PostgreSQL/shared deployments set `AUTO_CREATE_SCHEMA=false` and apply migrations explicitly.

## 3. No-Docker quick start (SQLite)

### Backend

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e "apps/backend[analytics,dev]"
python -m uvicorn app.main:app --reload --app-dir apps/backend --no-access-log
```

`--no-access-log` is intentional: the application emits its own JSON request log with
request ID, method, path, status, and latency, while omitting query strings, headers,
and bodies that may contain sensitive operational search terms.

The SQLite file is created in the repository working directory and ignored by Git. This profile is single-developer only.

Check the service in another terminal:

```powershell
Invoke-RestMethod http://localhost:8000/health/live
Invoke-RestMethod http://localhost:8000/health/ready
```

OpenAPI UI: `http://localhost:8000/docs`

### Frontend

In a second terminal at the repository root:

```powershell
npm --prefix apps/frontend install
npm --prefix apps/frontend run dev
```

Operator UI: `http://localhost:5173`

If PowerShell execution policy prevents virtual-environment activation, invoke `.\.venv\Scripts\python.exe` explicitly for the Python commands instead of weakening machine-wide policy.

## 4. Migrations

For a configured database, run Alembic from the backend directory so its relative migration path resolves predictably:

```powershell
Push-Location apps/backend
python -m alembic upgrade head
python -m alembic current
Pop-Location
```

Do not combine ad-hoc `create_all` behavior and manual schema changes in a shared environment. Migration history is the source of truth for PostgreSQL/PostGIS.

## 5. Full Compose profile (PostGIS + API + UI)

Review and replace the development database password in `.env`, then run:

```powershell
docker compose -f deployment/docker/compose.p0.1.yml config
docker compose -f deployment/docker/compose.p0.1.yml up --build -d
docker compose -f deployment/docker/compose.p0.1.yml ps
```

The backend waits for the database health check, applies Alembic migrations, and then starts. The frontend proxies `/api/` to the backend inside the Compose network.

Endpoints:

- UI: `http://localhost:5173`
- API: `http://localhost:8000/api/v1`
- OpenAPI: `http://localhost:8000/docs`
- readiness: `http://localhost:8000/health/ready`

Inspect logs without exposing environment values:

```powershell
docker compose -f deployment/docker/compose.p0.1.yml logs --tail 100 backend
docker compose -f deployment/docker/compose.p0.1.yml logs --tail 100 frontend
docker compose -f deployment/docker/compose.p0.1.yml logs --tail 100 postgres
```

Stop services while retaining database data:

```powershell
docker compose -f deployment/docker/compose.p0.1.yml down
```

The named `drishti_postgres_data` volume remains. Deleting that volume is destructive and is intentionally not part of routine commands.

### Manifest validation note

Docker is not available on every development workstation. Run `docker compose ... config` and a clean build on the target host before treating the manifest as verified. File presence or YAML readability alone does not prove image availability, migrations, health checks, or application startup.

## 6. Load representative data

Create the departments first:

```powershell
$base = "http://localhost:8000/api/v1"
Import-Csv database/seeds/departments.csv | ForEach-Object {
  $body = @{
    code = $_.code
    name = $_.name
    description = $_.description
  } | ConvertTo-Json
  Invoke-RestMethod -Method Post -Uri "$base/departments" `
    -ContentType "application/json" -Body $body
}
```

Use a fresh database or skip department codes that already exist before repeating this loader.

The camera CSV resolves these departments by stable `department_code`; no environment-specific UUID replacement is needed. Upload it next:

```powershell
curl.exe -X POST `
  -H "Idempotency-Key: local-seed-v1" `
  -F "file=@database/seeds/cameras.csv;type=text/csv" `
  "http://localhost:8000/api/v1/cameras/import?on_duplicate=error"
```

Use sanitized data only. Never copy a production RTSP URI or credential into a seed file.

## 7. Verification commands

Install dependencies first, then run:

```powershell
python -m pytest apps/backend/tests
python -m ruff check apps/backend
npm --prefix apps/frontend run test
npm --prefix apps/frontend run lint
npm --prefix apps/frontend run typecheck
npm --prefix apps/frontend run build
```

PostgreSQL/PostGIS requires a separate integration pass with `DATABASE_URL` pointed at the Compose database. A successful SQLite test run does not verify the PostGIS migration or spatial-query plan.

Record the exact command, timestamp, commit/archive identity, database profile, and result for hackathon evidence. Do not report a check as passed merely because it is listed here.

## 8. P0.1 manual acceptance walk-through

Use a fresh sanitized database and record the screen:

1. Confirm live/readiness checks.
2. Create two representative departments.
3. Add one camera manually, including valid Gujarat coordinates and capability metadata.
4. Attempt an invalid coordinate and show the validation error.
5. Import the representative CSV and inspect row-level results.
6. Filter the inventory by department, district, lifecycle, health, and AI capability.
7. Open the GIS view and camera detail.
8. Send a heartbeat; show the updated health and timestamp.
9. Update a safe metadata field; show the audit entry.
10. Retire a camera; verify it remains auditable and is not deleted.
11. Confirm that no UI/API response, seed, or log contains camera credential material.

## 9. Deployment hardening gate

The Compose profile is for evaluation/development, not an internet-facing production release. Before real feeds or sensitive inventory are introduced, add and test:

- OIDC authentication and department/district/camera-scoped RBAC/ABAC;
- TLS termination and mutual service identity where appropriate;
- a managed secret store and credential rotation;
- database encryption, least-privilege roles, backup/restore, HA, RPO/RTO tests;
- gateway request/body/rate limits and import malware/content controls;
- centralized structured logs, metrics, alerts, and tamper-resistant audit export;
- network segmentation and adapter egress allowlists;
- retention and disclosure policy for sensitive camera topology.
